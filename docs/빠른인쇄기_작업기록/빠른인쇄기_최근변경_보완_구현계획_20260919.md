## 5. 단계 1 — 예약 삭제와 이름 구분지 보정

### 5.1 현재 원인

`build_print_jobs()`는 연속된 같은 학생의 이름 구분지를 최초 블록에만 붙인다. `remove_reserved_blocks_from_active_print()`는 삭제 블록의 `block_uid` 작업을 모두 제거하므로 공유 구분지도 사라진다. `print_last_name_separator_label`은 삭제 후 갱신하지 않는다.

또한 기존 전송기는 미리 가져온 작업 목록을 순회할 수 있다. 삭제 후 새 구분지를 삽입하면, 예전에 가져온 본문 작업을 그대로 전송하여 새 구분지를 건너뛸 수 있다. **이름 보정과 전송 직전 최신 순서 확인을 함께 고친다.**

### 5.2 보존해야 할 조건

- 시작·전송·결과 미확정인 작업과 그 블록은 수정하지 않는다. `print_started_block_ids`가 기준이며 화면의 `예약` 글자만 믿지 않는다.
- 작업 목록에서 시작된 블록의 전체 작업은 보호한다. 부분 전송된 블록의 나머지 작업도 예약 삭제로 제거하지 않는다.
- 이미 처리한 접두부의 길이·작업 ID·순서는 변하지 않는다. 따라서 전송기의 현재 인덱스가 뒤로 이동하지 않는다.
- 남는 본문·OMR·일반 구분지 작업 ID는 유지한다. 새로 필요한 이름 구분지만 새 job ID를 받는다.
- 같은 이름의 연속 그룹 앞에 이름 구분지를 한 번만 둔다. 고정 백지리뷰/OMR가 이름 경계를 끊는 기존 규칙을 재사용한다.
- 삭제한 그룹 사이에서 같은 학생 그룹이 이어지면 중복되는 **미전송** 이름 구분지는 제거한다. 이미 보낸 구분지는 되돌리려 하지 않는다.

### 5.3 구현 인터페이스

`unit_print_queue_state.py`에 다음 역할의 순수 함수를 둔다. 이름은 구현에서 맞춰도 되지만 입력과 보존 조건은 지킨다.

```python
@dataclass(frozen=True)
class PendingNameRepair:
    jobs: tuple[Job, ...]
    removed_job_ids: tuple[str, ...]
    added_jobs: tuple[Job, ...]
    trailing_name_label: str

def reconcile_pending_name_groups(
    jobs, ordered_scheduled_blocks, removed_block_ids,
    protected_block_ids, *, enabled, preceding_name_label,
    make_name_separator_job,
) -> PendingNameRepair:
    ...
```

`ordered_scheduled_blocks`는 화면 전체가 아니라 해당 실행에 등록된 블록의 순서다. 아직 예약하지 않은 새 블록을 이 함수가 실행 큐에 끌어들이면 안 된다. `make_name_separator_job`은 기존 경로/템플릿을 재사용하는 메모리 작업이어야 한다. 파일 생성이나 Tk 호출은 하지 않는다.

알고리즘:

1. 삭제 대상이 보호 집합과 겹치면 전체 요청을 거부한다. 다중 선택에서 일부만 몰래 삭제하지 않는다.
2. 보존할 시작된 접두부와 미시작 블록 순서를 나눈다. 시작된 접두부는 작업 단위로 그대로 유지한다.
3. 앞 이름 문맥에서 시작해 남은 블록의 이름 경계를 계산한다. 기존 `normalize_name_separator_label`, `block_uses_name_separator`, `name_separator_group_labels` 규칙을 공통으로 사용한다.
4. 각 미시작 블록의 본문·OMR·일반 구분지는 순서와 ID를 유지한다. 필요한 이름 구분지가 없으면 앞에 추가하고, 불필요한 미전송 이름 구분지는 제거한다.
5. 새 구분지에는 남는 블록의 `block_uid`, `block_index`, `block_summary`, `history_block`을 넣고 fresh job ID를 발급한다. 삭제한 블록의 학생/주문 이력을 새 작업에 남기지 않는다.
6. 최종 남은 작업의 이름 문맥으로 `print_last_name_separator_label`을 갱신한다. 고정 양식 또는 빈 실행 큐 처리도 명시한다.

앱 통합:

- 단일/다중 삭제가 동일한 보정 경로를 사용한다. 작업 목록·예약 집합·마지막 이름·큐 revision을 `print_state_lock` 안에서 일관되게 갱신한다.
- PDF가 필요하면 잠금 밖에서 준비하고, 잠금 안에서 revision과 시작된 집합을 재확인한다. 그 사이 전송이 시작되었으면 최신 상태로 다시 계획한다. 긴 PDF 처리나 네트워크 호출을 잠금 안에 넣지 않는다.
- `claim_active_print_job()`는 단순 job ID 존재 확인을 넘어 **현재 전송 인덱스의 작업 ID가 요청과 같은지** 검증한다. 목록 revision 변경을 감지하면 최신 목록을 다시 가져온다.
- 롤링/직렬/기존 Sumatra 경로 모두 적용한다. 기존 경로가 미리 가져온 배치를 순회하다 변경을 감지하면 남은 로컬 배치를 폐기하고 현재 인덱스부터 다시 가져온다. 실패한 claim은 전송 수나 인덱스를 증가시키지 않는다.
- 이력에는 삭제한 job ID, 제거한 구분지 job ID, 추가한 구분지 job ID와 이유를 연결한다. 필요한 변경 이력 실패 시 변경/후속 전송을 성공으로 처리하지 않는다. 기존 필수 `job_attempt`/`job_submitted` 저장 순서는 유지한다.

### 5.4 재시도·되돌리기

`RetryBatch.jobs`만으로는 이미 출력한 이름 구분지를 알 수 없다. 재시도 옵션을 `any(job.is_name_separator)`로 복원하면 마지막 구분지가 이미 전송된 경우 이름 기능 자체가 꺼질 수 있다.

- `RetryBatch`에 옵션과 앞 이름 문맥을 담는 기본값 있는 필드를 추가한다. 최소 `name_separator_enabled`와 `preceding_name_separator_label`이 필요하다. 일반 구분지 옵션도 기존 옵션에서 보존한다.
- `preserve_retry_from_failure()`는 이미 전송했거나 재전송 금지인 접두부의 문맥과 실제 실행 옵션을 저장한다.
- `retain_visible_retry_jobs()`, `sync_retry_queue()`, `QueueSnapshot`, undo, 재시도 시작 시 이 메타데이터를 버리지 않는다.
- 재시도 목록에서 블록을 지울 때도 같은 보정 함수를 사용하되, 이미 보낸 이름 구분지를 새로 생성하지 않는다.
- 앱 재시작 후 자동 복구/재인쇄는 추가하지 않는다. 이 문맥은 현재 세션의 미전송 재시도에 한정한다.

```python
class RunPhase(StrEnum):
    IDLE = "idle"
    PREPARING = "preparing"
    RUNNING = "running"
    HELD = "held"
    STOPPING = "stopping"
    STOPPED = "stopped"
    ERROR = "error"
    COMPLETE = "complete"

@dataclass(frozen=True)
class PrintProgressState:
    run_id: str | None
    phase: RunPhase
    completed: int
    total: int
    hold_reason: str
    completion_pending: bool
    completion_basis: str  # device / windows_spooler / none
```

핵심 규칙:

- 진행률 이벤트는 완료 수·전체 수만 갱신한다. HELD/STOPPING/STOPPED/ERROR/COMPLETE를 RUNNING으로 바꾸지 않는다.
- 새 실행 ID 시작과 현재 실행의 재개 확정이 상태를 바꾼다. 이전 실행에서 늦게 도착한 callback은 무시한다.
- 장비가 정상으로 돌아온 사실만으로 재개 표시를 하지 않는다. 사용자 `해결 후 이어서`와 장비 작업 재조정이 끝난 시점에 RUNNING으로 전환한다.
- 정지·오류 중 현재 작업 문구는 원인·해결 안내를 유지한다. 완료 수가 바뀌면 그 뒤에 진행 정보를 붙일 수 있다.
- 완료 상태의 늦은 진행률 이벤트가 배지를 지우면 안 된다. 배지는 앱 내부 확인 또는 새 인쇄 시작으로만 지운다.
- 장비 모드 완료 근거는 토큰이 일치하는 실제 완료다. Windows 전용 모드의 기존 완료 의미는 `windows_spooler`로 구분하고 실물 확인으로 기록하지 않는다. 미리보기 완료에는 인쇄 완료 배지를 남기지 않는다.

통합 지점은 `set_status`, `set_current_work`, `set_taskbar_print_progress`, `enter_device_hold`, `resume_device_print`, 취소, 각 worker 종료 분기다. 상태 모델을 기준으로 기존 한글 라벨과 작업 표시줄 표시를 만든다. 서로 다른 함수가 각각 독립된 실행 상태를 유지하게 두지 않는다.

Tk/COM 반영은 UI 스레드에서 한다. 변경 없는 화면 쓰기·큐 전체 다시 그리기를 생략하는 기존 최적화와 4단계 양자화는 유지한다.

## 7. 단계 3 — Windows 작업 표시줄 수명 관리

`unit_print_taskbar.py`에 `TaskbarWindowHook`과 재적용 인터페이스를 추가한다. 새 외부 패키지는 필요하지 않다.

1. 실제 작업 표시줄을 소유한 Tk 최상위 HWND를 구한다. `RegisterWindowMessageW("TaskbarButtonCreated")`를 등록하고 `SetWindowSubclass`로 앱 자신의 창에 콜백을 연결한다.
2. 창이 처음 표시되기 전에 연결한다. `main()`/생성자 초기 순서를 확인해, 기존 `update_idletasks()` 등으로 창이 매핑된 뒤 350ms 기다리는 방식에 의존하지 않는다. 초기 UI 구성·위치·표시 타이밍을 불필요하게 바꾸지 않는다.
3. 생성 메시지를 받으면 ready generation을 증가시키고 UI 이벤트 처리로 초기화/복구를 예약한다. Win32 콜백 안에서 PDF·네트워크·긴 COM 작업을 하지 않는다.
4. 같은 UI 스레드에서 COM을 초기화하거나 재연결하고 `_last_progress`, `_overlay_kind`를 무효화한 뒤 현재 상태를 강제로 적용한다. 같은 숫자 `1`이어도 새 작업 표시줄에는 다시 설정한다.
5. 초기화 실패는 로그에 남기고 표시 기능만 제한한다. 인쇄를 막지 않는다. 재시도는 ready 메시지 수신 뒤에만 제한적으로 수행하며 매 문서마다 반복하지 않는다.
6. `RemoveWindowSubclass`, `DefSubclassProc`, `WM_NCDESTROY` 처리와 명시적 close를 구현한다. 중복 close를 허용하고 모든 메시지를 정상 체인으로 전달한다.
7. ctypes 함수의 `argtypes/restype`, `LRESULT/WPARAM/LPARAM/UINT_PTR/DWORD_PTR`를 포인터 크기에 맞춘다. Python callback 참조를 후킹 해제까지 유지한다. `DestroyIcon`도 명시적 HICON/BOOL 서명을 사용한다.

후킹 설치·제거·COM은 창 소유 UI 스레드에서만 수행한다. 문서 근거: [SetWindowSubclass](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-setwindowsubclass), [DefSubclassProc](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-defsubclassproc), [ITaskbarList3](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-itaskbarlist3), [SetOverlayIcon](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist3-setoverlayicon).

실제 Explorer 프로세스를 자동으로 종료하는 검사는 하지 않는다. 가짜 Windows API 계층과 앱의 생명주기 통합 검사로 메시지 수신·재적용·해제를 검증한다. 실제 Explorer 재시작 확인 여부는 별도로 기록한다.

## 8. 단계 4 — PDF 준비를 화면 처리에서 분리

### 8.1 데이터와 스레드 경계

`unit_print_preparation.py`에 다음 역할의 불변 DTO를 둔다.

```python
SourceSignature = tuple[str, int, int]  # resolved path, size, mtime_ns

@dataclass(frozen=True)
class PdfRecipe:
    sources: tuple[SourceSignature, ...]
    pages: tuple[int, ...] | None
    operation: str  # select_pages / merge_documents / four_up
    layout_version: str

@dataclass(frozen=True)
class PreparedPdf:
    recipe_key: str
    path: Path
    source_signatures: tuple[SourceSignature, ...]
```

실제 필드는 각 operation을 모호하지 않게 표현하도록 조정한다. 여러 입력 파일의 페이지 선택이 필요하면 파일별 페이지 목록을 둔다. path·정수·문자열·frozen catalog 값만 worker에 전달한다. Tk 변수, 위젯, 변경 가능한 앱 객체, 공유 PdfReader/PdfWriter는 전달하지 않는다.

UI는 자료·차시·부수·이름·경로·프로필·입력 revision을 한 번 캡처한다. worker는 파일 검사·추출·병합·조판만 수행한다. 완료 결과는 thread-safe 결과 큐에 넣고, UI가 예약된 짧은 `after` 콜백으로 반영한다. 작업 없는 idle 상태에서 폴링을 계속하지 않는다.

### 8.2 A:ble·대량 주문서 통합

- `make_able_lesson_files()`를 선택 계산과 실제 파일 생성으로 나눈다. 기존 공개 동기 경로는 CLI/기존 테스트가 재사용할 수 있게 두고, GUI `add_able_material_block()`은 비동기 준비를 사용한다.
- `교재 + 백지리뷰`의 결과는 교재 선택분 하나와 백지리뷰 선택분 하나다. `3,1` 같은 선택 순서, 구간 간격, 교재 4면/리뷰 1면, 묶음 부수 순서를 유지한다.
- `add_order_csv_blocks()`는 CSV와 읽기 전용 catalog/profile 스냅샷으로 행별 초안을 만들고, 무거운 자료 생성을 백그라운드로 넘긴다. `resolve_order_csv_blocks`와 기존 자료별 계산 규칙을 재사용한다. 앱 객체를 통째로 worker에서 호출하거나 APEX·트레이닝팩의 페이지 규칙을 새로 복제하지 않는다.
- 주문 배치는 전체 준비·검증 성공 뒤 한 번에 커밋한다. 오류가 있으면 기존처럼 행 번호를 표시하고 큐를 부분 변경하지 않는다.
- 새 주문 배치만 NFC 이름 기준 안정 정렬하고, 같은 학생의 CSV 상대 순서와 기존 큐 순서는 유지한다. undo/history는 배치당 한 번의 논리적 추가로 남긴다.
- 자료 준비 안내는 기존 자료 입력 영역의 상태 문구를 사용한다. 인쇄 중 전역 상태나 프린터 정지 안내를 덮지 않는다.

### 8.3 비동기로 바뀌면서 반드시 처리할 경우

- 요청 시 입력을 고정한다. 작업 중 사용자가 차시·이름을 바꾸어도 이전 요청의 결과가 새 입력과 섞이지 않는다.
- 완료 시 사용자가 이미 새 입력을 시작했다면 그 새 입력을 지우거나 부수를 1로 되돌리지 않는다. 동일 입력 revision에 대해서만 기존 후처리를 한다.
- 모든 블록 추가의 커밋은 사용자가 요청한 순서를 지킨다. 느린 A:ble 준비 중 추가한 빠른 PDF 블록이 앞서 들어가지 않도록 공통 추가 경로에 요청 순번을 적용한다. 실패/취소된 요청은 순번을 해제해 후속 요청이 막히지 않게 한다.
- 대기 중 중복 버튼/단축키 제출을 제어하되 UI 전체를 잠그지 않는다. 다른 선택·큐 탐색은 가능해야 한다.
- 큐 비우기, 준비 취소, 앱 종료, 자료 루트 변경 후에는 이전 결과가 블록을 되살리지 못하게 요청 epoch를 검사한다. 선택 블록 수정에 준비가 필요하면 대상 ID·입력 revision도 확인한다.

### 8.4 캐시와 서비스 제한

- 작업이 처음 필요할 때 준비 worker를 만든다. 시작 시 새 PDF 전수 조사나 여러 worker를 띄우지 않는다.
- PDF worker는 우선 1개로 제한한다. 실행 중 인쇄의 다음 준비 작업을 일반 추가 작업보다 우선하며, 대량 주문서는 파일 단위로 나눠 우선 작업이 끼어들 수 있게 한다. 이미 실행 중인 한 번의 pypdf 호출을 강제로 중단하지 않는다.
- 동일 recipe/signature는 한 번만 계산한다. 여러 작업이 같은 준비 결과를 참조해도 실제 인쇄 job ID·전송 토큰은 각각 유지한다.
- 캐시 키에 입력 순서, 정규 경로, 파일 크기·수정 시각, 선택 페이지, operation/layout 버전을 포함한다. `materialize_pdf_pages()`의 현재 키에도 size를 포함한다.
- `materialize_pdf_pages/documents`의 고정 `.tmp.pdf` 이름을 같은 디렉터리의 고유 임시 파일과 원자적 replace로 바꾼다. 동시에 같은 결과를 만드는 경우도 완성된 파일만 캐시로 인식한다.
- 시작 전후 입력 서명이 달라지면 결과를 성공으로 사용하지 않는다. 전송 시에도 재확인한다. 준비 캐시는 기존 preflight·필수 이력을 대신하지 않는다.
- 종료 때 새 작업 접수를 막고 대기 작업을 취소한다. 실행 중 파일 쓰기는 완료/정리할 수 있게 하며 GUI를 멈춘 채 `join()`으로 기다리지 않는다. `on_close`/`finish_close_when_idle`에 준비 수명도 연결한다.

근거: [Tkinter 스레딩 모델](https://docs.python.org/3.12/library/tkinter.html#threading-model). `append/merge`가 권장 API라는 사실만으로 교체하지 않는다. [pypdf 병합](https://pypdf.readthedocs.io/en/6.16.2/user/merging-pdfs.html), [압축 비용](https://pypdf.readthedocs.io/en/6.16.2/user/file-size.html).

## 9. 단계 5 — 다음 2건 사전 준비와 전송 연결

사전 준비는 파일 계산이다. **예약하거나 실제 프린터로 보내는 행위와 구분한다.** Canon의 기본 선전송 창 6건과 접수 확인 정책은 그대로 둔다.

1. 각 실행은 run ID로 준비 결과를 관리한다. 현재 작업과 다음 최대 2개 작업의 조판 결과만 요청한다. 같은 경로·레이아웃이면 결과를 공유한다.
2. 사전 준비만으로 `print_started_block_ids`에 넣지 않는다. 따라서 아직 시작하지 않은 예약 블록은 계속 삭제할 수 있다.
3. 전송기는 최신 큐의 다음 작업을 가져와 준비를 확인한다. 준비를 기다리는 동안 취소·장비 정지·큐 변경을 확인한다.
4. 준비 완료 후 원본 서명과 작업 존재를 재검사하고, 단계 1의 최신 순서 claim을 통과한 뒤 전송한다. 먼저 준비된 뒷 작업을 앞서 보내지 않는다.
5. claim 후 필요한 필수 이력 → Sumatra → 제출 결과 처리는 기존 순서를 지킨다. 제출/미확정 경계를 넘은 작업은 자동 재전송하지 않는다.
6. Canon에 정확한 앞 작업 토큰이 나타나기 전에는 다음 작업을 제출하지 않는다. 장비가 정지하면 보충도 정지한다. 재개는 기존 장비 작업 재조정 뒤에 수행한다.
7. 삭제·정지·새 실행으로 무효화된 future는 전송에 사용하지 않는다. 공유 중인 정상 디스크 캐시는 남겨도 되지만 이전 실행의 제출용 토큰 파일을 재사용하지 않는다.
8. 뒤 작업의 준비 오류는 그 작업이 실제 차례에 도달했을 때 일관되게 보고한다. 조용히 건너뛰지 않으며, 이미 전송한 앞 작업의 상태를 되돌리지 않는다. 앞 작업의 정상 진행까지 미리 실패 처리하지 않는다.

롤링, 직렬 호환 경로, 기존 Sumatra 경로가 하나의 준비 API를 사용한다. 드라이런은 준비/순서 검증이 가능하되 프린터 호출은 차단한다. 이 성능 패치에서 디바이스 polling 간격을 임의로 줄이거나 동시 전송을 추가하지 않는다.

## 11. 성능 검증과 완료 판정

기존 기준은 공통수학1 1·2·3차시, 교재 96쪽·리뷰 3쪽, 4면 결과 24면이다. 현재 환경의 파일 준비 합계는 캐시 없음 0.409–0.442초, 캐시 사용 0.0018–0.0024초였다. 이 값은 실물 인쇄 시간이 아니다.

- 비교 환경은 동일 핀·같은 PDF·같은 컴퓨터로 고정한다. pypdf 버전을 바꾸어 생긴 차이를 코드 개선으로 보고하지 않는다. 핀 환경에서 수정 전 기준도 별도로 확보한다.
- 준비 서비스 API의 UI 진입 handler가 PDF 작업을 직접 기다리지 않는 것을 결정적 테스트로 확인한다. 실제 비인쇄 GUI 측정은 20ms heartbeat를 두고 준비 중 최대 지연과 p95를 기록한다. 목표는 p95 100ms 이하이며 측정 환경 영향을 함께 적는다.
- 캐시 없음/있음, A:ble 3차시/전체, 같은 선택 반복 주문/다른 선택 혼합 주문을 측정한다. 준비 시간, 전송기가 준비를 기다린 시간, 중복 생성 횟수, 대기 준비 수를 구분한다.
- 성능 비교는 워밍업 후 5회 중앙값을 사용한다. 기준 대비 PDF 계산 자체가 20% 넘게 느려지거나 CPU/메모리가 급증하면 이유를 조사한다. 타이밍 숫자를 일반 CI의 불안정한 단일 실행 assertion으로 넣지 않는다.
- 가짜 장비의 접수·완료 간격을 고정해 사전 준비가 다음 제출의 준비 대기를 줄이는지 확인한다. 가짜 장비 결과를 실제 프린터 속도 개선으로 표현하지 않는다.
- 화면 응답·순서·취소 검증을 통과하지 않으면 worker 수를 늘리는 방식으로 마무리하지 않는다.

## 12. 배포·문서·최종 검사

1. `scripts/build_quick_printer_release.py`의 `APP_FILES`에 새 실행 모듈과 환경 검증 스크립트를 넣고 릴리스 테스트에서 포함 여부를 검사한다. 리뷰 증거·이력·학생 데이터·캐시·로컬 설정은 배포 대상에 넣지 않는다.
2. 정본에 예약 삭제 후 이름 경계 보정, 정지 표시 우선순위, 배지 복구, 비동기 준비 중 입력/순서 계약을 반영한다.
3. README에 작업 중 자료 준비와 실제 인쇄의 상태 의미, 예약 삭제 범위, 동일 환경 검증 명령을 반영한다. AGENTS의 “예약 블록은 보호” 같은 오래된 포괄 문장을 현재 시작 여부 기준으로 고친다.
4. 변경에 맞는 타깃 검사가 통과하면 동일 핀 환경에서 아래 전체 검사를 한 번 수행한다. 실패나 추가 변경이 없다면 같은 검사를 불필요하게 반복하지 않는다.

`verify_quick_printer_environment.py` 등 신규 파일을 구현한 뒤 실행하는 명령이다. 문서 작성 시점에 존재하는 것처럼 취급하지 않는다.

최종 결과 문서 `output/quick_printer_stabilization_20260919/implementation_results.md`에는 다음을 남긴다: 변경 파일·이유, 위 검사별 결과, 실제 사용 인터프리터·패키지 버전, 수정 전후 측정, 실제 실행하지 못한 장비/Windows UI 검사, 남은 문제. 테스트 개수만으로 완료를 선언하지 않는다.

프로젝트 AGENTS의 `Do not trigger live printing or driver dialogs during investigation without explicit current-task approval.` 규칙을 따른다. 이 계획의 자동 검증은 실물 출력과 드라이버 조작 없이 완료한다. 실제 출력 검사가 필요하면 코드·테스트·출력할 샘플과 예상 매수를 먼저 준비한 뒤 해당 행위만 별도로 확인받는다. 현재 런타임에서 제한된 네이티브 UI 제어를 다른 helper로 우회하지 않는다.

## 13. 실행 순서와 전달 프롬프트

권장 순서: **환경 확인·재현 테스트 → 예약 삭제/재시도 → 상태 모델 → 작업 표시줄 복구 → 비동기 자료 준비/캐시 → 사전 준비 통합 → 회귀·성능·배포 검사 → 문서 갱신**.

단계별로 관련 검사를 통과한 뒤 다음 단계에 들어간다. 단일 작업에서 계속 진행하며 별도 작업 생성이나 모델 자동 변경은 필요하지 않다. 모든 단계의 완료 여부를 최종 결과 문서에 표시한다.
