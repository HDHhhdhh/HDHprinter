# 빠른 인쇄기 안정화와 파일 보존

작성: 2026-09-30

후속 GUI 시작 지연 수정과 최신 전체 회귀 763개 결과는 `빠른인쇄기_GUI시작_수정_20260930.md`를 참고한다. 아래의 758개 결과는 그 이전 안정화 시점 기록이다.

파일 삭제 사건 이후 필요한 소스·자료 보존, 실행 진단, 중복 실행 방지와 단계별 구조 분리를 구현했다. 인쇄 순서·실제 완료 판정·미확정 전송 보류·빈 큐 시작·수동 복구 계약을 유지한다. 기존 실행 중인 앱을 종료하거나 프린터에 테스트 문서를 보내지는 않았다.

## 실행과 중복 실행

- CMD/VBS/직접 Python 실행은 stdlib `unit_print_bootstrap.py` 한 경로로 들어간다. 필수 파일 46개, Python 3.12와 패키지 존재를 검사하며 PDF 전체 해시는 실행 때마다 읽지 않는다. 단원평가 JSON이 없는 경우 기존 폴더 스캔을 유지한다.
- `unit_print_instance.py`는 Windows 사용자 SID를 사용한 Global mutex를 앱 수명 동안 유지한다. 설치 위치·Windows 세션이 달라도 같은 사용자의 두 번째 앱은 큐나 GUI를 만들지 않는다. 잠금을 확인할 수 없는 경우에도 실행을 차단한다.
- 실제 Windows에서 별도 UUID 이름의 테스트 프로세스로 동시 실행 차단과 프로세스 강제 종료 후 잠금 계승을 확인했다. 생산 앱의 잠금·GUI·프린터는 건드리지 않았다. 다른 사용자/PC와 외부 인쇄 프로그램은 이 잠금 범위 밖이다.
- 누락·초기화 실패·Tk 콜백·스레드 예외는 진단 로그와 안내로 남긴다. 로그에는 예외 원문, 로컬 변수, 설정값과 PIN을 넣지 않는다. 앱 폴더 기록 실패 시 LOCALAPPDATA/임시 폴더로 대체한다.
- 런처는 Python 3.12를 선택하고, 설치기는 pip 실패와 고정 의존성 불일치를 설치 성공으로 처리하지 않는다. VBS의 한국어 안내는 UTF-16 BOM으로 보존한다.

## 구조와 실패 처리

- `unit_print_domain.py`로 인쇄 모델과 순수 이름·OMR·라우팅·A:ble 규칙을 옮겼다. 기존 manager import API는 같은 클래스 객체를 계속 제공한다.
- `unit_print_execution.py`로 실행 메서드 13개를 옮겼다. manager가 명시적인 `PrintExecutionServices`를 제공하고 실행 모듈은 manager를 다시 import하지 않는다. UI 값은 실행 옵션으로 전달하며 Tk 상태 갱신은 기존 메인 스레드 경계를 사용한다.
- 장비 모니터가 없거나 PDF 준비 객체 생성에 실패해도 실행 플래그·예약 상태가 남지 않는다. 전송하지 않은 원본 작업과 부수를 재시도로 보존하고, 실제 전송 시도가 없었음을 회귀 검사로 확인한다.
- Canon 감사 기록의 `printed_pdf`는 실제 전송한 토큰 사본의 SHA다. 준비 원본 경로는 `prepared_pdf_path`로 분리했다. 사본 생성 후 원본이 바뀌어도 감사 해시는 실제 전송 바이트와 일치한다.
- 사본 삭제는 앱 전용 스풀의 토큰 PDF 직접 하위 파일만 허용한다. 원본·외부 경로·심볼릭 링크를 거부한다. 삭제 실패로 물리 인쇄 완료 판정을 뒤집지 않는다.

메인 GUI/카탈로그 클래스는 아직 크다. 이번 작업은 핵심 모델과 실행 경계를 분리한 것이며 모든 GUI 구조 문제 제거를 의미하지 않는다. 전송마다 새 PowerShell 조회·복구 fsync를 추가하지 않았다. 실제 전송 사본 해시 검증은 파일 읽기를 추가하며 실물 출력 속도 개선은 이번 검사로 주장하지 않는다.

## 자료와 백업

새 로컬 자료 루트는 `C:/Users/gkseh/Documents/빠른인쇄기_자료_검증본_전체`다. 등록 PDF **1,852개 / 6,547,947,176 bytes**를 `data`에 복사해 원본·복사본 SHA를 전수 검증했다. 교과서 141개는 현재 카탈로그의 크기·SHA·페이지 수로 검증했고, 42개 판본을 유지한다. 일반 검사 환경에서 모든 PDF의 읽기와 교과서 페이지 수를 다시 확인했다. 로컬 `release_root`와 기존 관리 루트에 속한 단원평가 `root_dir`를 새 위치로 전환했다. 바탕화면·C/D 원본과 이전 복사본은 삭제하지 않았다.

`scripts/quick_printer_safe_assets.py`는 원본을 바꾸거나 기존 대상을 덮어쓰지 않는다. 크기·SHA·필요한 페이지 수를 임시 형제 폴더에서 검증한 후 완성된 새 폴더만 공개한다. 복사 실패·원본 변경·목적지 경쟁 시 기존 파일을 보존한다. 처음 복사한 폴더의 제한 권한을 발견해 도구의 staging을 부모 권한 상속 방식으로 고쳤다. 기존 트리 권한 변경은 자동 승인 심사에서 거절돼 수행하지 않았고, 새 검증 복사본 생성으로 해결했다.

독립 안전백업은 OneDrive 작업 폴더 밖의 `C:/Users/gkseh/Documents/빠른인쇄기_안전백업/20260930_203409`에 보존한다. 수정 전 소스 132개와 Git 잔여 객체를 먼저 보관했고, 등록 PDF 1,852개도 별도로 검증 복사했다. 최종 소스·검사·문서와 운영 설정·이력·큐 복구 정보·생성 PDF는 구분해서 보관한다. 운영 데이터는 개인정보가 있는 로컬 백업이며 Git·배포본·Drive에 포함하지 않는다. Credential Manager의 PIN을 내보내지 않는다. 운영 백업은 파일별 일관성을 확인한 시점 보관이며 앱 전체의 동시 트랜잭션 스냅샷이나 인쇄 상태 자동 복구가 아니다.

## Git와 과거 삭제 사건의 한계

기존 `.git`의 HEAD/config/index를 되살리는 과정에서 과거 Codex 스냅샷이 참조하는 객체 7개가 실제로 유실된 것을 확인했다. 손상 메타데이터는 백업에 그대로 보존했다. 검증된 수정 전 소스로 기준 커밋을 만들고 정상 객체만 가져온 저장소를 구성했으며 `git fsck`를 통과했다. 현재 수정본도 이 기준과 비교해 보관한다. 원격 push는 하지 않았다.

이는 **현재 소스의 버전 관리를 정상화한 것**이다. 유실된 과거 객체나 삭제 직전 모든 파일을 완전히 복구했다는 뜻은 아니다. 모듈이 빠진 9월 28일 압축 해제 배포 폴더를 현재 소스 위에 덮어쓰지 않았다. 신규 최종 소스 백업에는 필수 모듈을 모두 포함하고 기존 배포 수집 목록에도 신규 모듈 5개를 반영했다. 과거 Drive 배포물의 상태는 확인하지 않았고 새 배포본 제작/업로드도 수행하지 않았다.
