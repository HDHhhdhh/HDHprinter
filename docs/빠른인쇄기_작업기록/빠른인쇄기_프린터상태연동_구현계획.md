# 빠른인쇄기 프린터 상태 연동 구현 계획

작성일: 2026-09-18 / 최종 갱신: 2026-09-19  
대상: Windows Python 3.12 / Tkinter 빠른 인쇄기 / Canon iR-ADV 8585 III  
문서 상태: 구현 기준 및 회귀 검증안. 실물 인쇄는 별도 승인과 운영 검증이 필요하다.

이 계획은 스테이플 부족 등 장비 오류 알림, 블록 순서 유지, 장비가 보고한 출력 완료 확인, 예상 남은 시간, A4 잔량 표시를 함께 구현한다. 기존 디자인·단축키·자료 구성·스테이플 설정은 유지하고, 상태 표시와 필요한 연결 화면만 추가한다.

## 1. 이번 구현에서 확정할 기본 방향

1. 현재 조회에 성공한 Canon Remote UI를 1차 정보원으로 사용한다. Windows 대기열은 보조 정보원이다.
2. 세로·가로·구분지·A:ble 프로필을 같은 물리 프린터의 한 전송 순서로 묶는다.
3. 순서 우선 모드에서는 앱 큐 순서대로 미완료 전송 작업을 프린터 한 대당 기본 6개(인쇄 중 1개와 대기 약 5개, 설정 1~10개)로 제한한다. 장비 완료 1건을 확인할 때마다 다음 대기 작업 1건을 즉시 보충한다. 각 전송 직후에는 빠른 활성 작업 목록에서 해당 토큰의 장비 접수만 확인하고, 전체 상태·소모품·완료 이력 조회는 별도 주기로 수행한다.
4. 오류·연결 끊김·전송 결과 불명확 상태에서는 추가 전송을 보류한다. 복구 후에는 상태를 대조하고 사용자의 “이어서” 동작으로 진행한다.
5. A4는 카세트별 잔량 구간을 표시한다. 센서가 제공하지 않는 정확한 남은 매수는 만들어 내지 않는다.
6. 남은 시간은 실제 정상 처리 표본으로 계산한 예상 범위로 표시한다. 오류 중에는 완료 예정 시각을 보류한다.
7. 기존 자동 재시도의 대상을 “확실히 아직 보내지 않은 작업”으로 좁힌다. 전송을 시도했지만 결과를 모르는 작업은 별도로 확인한다.

“장비 완료 확인”은 Canon이 해당 작업을 성공 종료로 보고했다는 뜻이다. 사람이 출력물을 확인했다는 뜻으로 기록하지 않는다. 스테이플 마감까지 해당 종료 시각에 포함되는지는 실물 인수검사에서 검증한다.

## 2. 확인한 사실과 아직 검증할 사항

### 2.1 실제 장비에서 확인한 정보

2026-09-18 원격 관리 화면에서 다음 정보를 읽었다. 잔량과 오류 상태는 조회 당시 값이며 현재 상태로 고정해서 사용하지 않는다.

| 정보 | 확인 결과 | 구현 시 해석 |
|---|---|---|
| 로그인 | 부서 ID / PIN 로그인 후 조회 가능 | 앱의 독립 로그인 세션 필요 |
| 장비 상태 | 인쇄 가능, 에러 없음 | 정상·오류·정보 미확인을 구분 |
| A4 카세트 1 | 66–100%, 양호 | 범위를 그대로 표시 |
| A4 카세트 2 | 66–100%, 양호 | 카세트 1과 별도 표시 |
| 카세트 3 / 4 | B4 / A3 | A4 잔량 계산에 넣지 않음 |
| 스테이플 / 중철 스테이플 | 각각 양호 | 두 종류를 별개 상태로 저장 |

| 작업 이력 | 접수번호, 시작·종료 시각, 원고·출력 페이지, 매수×부수, 종료코드 | 완료 판정과 작업 연결에 사용 |
| Windows 인쇄 프로필 | 여러 프로필이 같은 TCP/IP 포트를 사용 | 이름별이 아닌 물리 장비별로 전송 제어 |
| Windows 포트 SNMP | 비활성 | Windows 상태만으로 상세 오류를 판단하지 않음 |

Windows 포트의 SNMP 비활성은 프린터 본체의 SNMP 기능까지 꺼졌다는 증거는 아니다. 이번 버전은 확인된 Remote UI 경로를 사용하며, 상태 조회를 위해 Windows 포트 설정부터 변경하지 않는다.

Canon은 Remote UI의 상태·작업 이력 조회 기능을 안내하지만, 해당 CGI 경로를 안정적인 공개 API로 보장한 문서는 확인하지 못했다. 따라서 장비별 어댑터와 응답 형식 검증이 필요하다. [Canon 공식 설명](https://oip.manual.canon/USRMA-3800-zz-PS-8500-enUS/contents/devu-mcn_mng-rui-check_status_log.html)

### 2.2 구현 첫 단계에서 검증할 사항

- Python 클라이언트의 정상 로그인, 세션 만료 감지, 같은 계정의 브라우저 접속과 충돌 여부.
- 원격 UI 로그인 요청의 실제 action/method/필드/토큰. 로그인 제출 주소나 PIN 필드명을 추측해서 고정하지 않는다.
- 진행 중 작업의 접수번호·문서명·상태·페이지 진행량 제공 여부.
- 고유 파일명이 작업 상황과 완료 이력에 유지되는지, 어느 길이부터 잘리는지.
- 다부수·양면·4분할의 페이지/매수 필드 의미와 인쇄 작업 분할 여부.
- 현재 부서 계정으로 다른 부서 작업까지 보이는지. 보이지 않는 작업을 “없음”으로 간주하지 않는다.
- 완료 이력의 보존 개수, 갱신 지연, 장비 재부팅 시 접수번호 재사용 여부.
- 스테이플·용지 부족 상태의 실제 문구와 오류 항목. 정상 화면만 보고 오류 문구를 확정하지 않는다.

이 검증이 끝나기 전에는 “현재 N쪽 출력 중”이나 “물리 출력 순서 검증 완료”를 표시하지 않는다.

## 5. 데이터 구조와 API 초안

아래 코드는 구현 계약을 설명하는 초안이며 완성된 실행 코드가 아니다.

~~~python
from dataclasses import dataclass
from datetime import datetime
from enum import StrEnum
from typing import Protocol

class Quality(StrEnum):
    FRESH = "fresh"
    STALE = "stale"
    UNKNOWN = "unknown"

class SupplyLevel(StrEnum):
    OK = "ok"
    LOW = "low"
    EMPTY = "empty"
    UNKNOWN = "unknown"

@dataclass(frozen=True)
class PaperTray:
    tray_id: str
    label: str
    size: str | None
    paper_type: str | None
    level: SupplyLevel
    percent_range: tuple[int, int] | None
    eligible: bool | None  # 이번 출력에 사용 가능한 급지함인지
    observed_mono: float
    quality: Quality

@dataclass(frozen=True)
class DeviceJob:
    device_key: str
    receipt_number: str | None
    document_name: str
    attempt_token: str | None
    state: str  # accepted / processing / completed / failed / cancelled / unknown
    started_at: datetime | None
    ended_at: datetime | None
    output_pages: int | None
    sheets_per_copy: int | None
    copies: int | None
    result_code: str | None
    observed_mono: float

@dataclass(frozen=True)
class DeviceSnapshot:
    device_key: str
    generation: int
    received_mono: float
    authenticated: bool
    health: str  # ready / busy / blocked / unknown
    errors: tuple[str, ...]
    staple: SupplyLevel
    saddle_staple: SupplyLevel
    toner_percent: int | None
    trays: tuple[PaperTray, ...]
    active_jobs: tuple[DeviceJob, ...]
    recent_jobs: tuple[DeviceJob, ...]
    source_quality: dict[str, Quality]
    source_received_mono: dict[str, float]
    job_visibility: str  # all / department / unknown

class DeviceStatusProvider(Protocol):
    def read_health(self): ...
    def read_supplies(self): ...
    def read_active_jobs(self): ...
    def read_recent_jobs(self): ...
    def close(self) -> None: ...
~~~

통신 실패·누락 값은 None / UNKNOWN으로 표현한다. 빈 목록·0%·완료로 치환하지 않는다.

내부 코드 식별자는 영어, 운영자에게 보이는 문구는 기존 프로젝트의 한국어 표현을 사용한다. 관측 dict는 생성 후 수정하지 않고 새 스냅샷으로 교체한다.

전송 원장은 전송 결과와 장비 결과를 별개 필드로 저장한다.

~~~python
class SubmissionState(StrEnum):
    NOT_SENT = "not_sent"
    IN_FLIGHT = "in_flight"
    CALL_CONFIRMED = "call_confirmed"
    UNCONFIRMED = "unconfirmed"

class CompletionState(StrEnum):
    NOT_OBSERVED = "not_observed"
    ACCEPTED = "accepted"
    PROCESSING = "processing"
    DEVICE_CONFIRMED = "device_confirmed"
    FAILED = "failed"
    CANCELLED = "cancelled"
    NEEDS_REVIEW = "needs_review"

@dataclass
class TrackedJob:
    job_id: str                  # 기존 PrintJob.job_id
    block_history_id: str        # UUID; id(block)을 대체하지 않음
    block_uid: int               # 현재 세션 UI 연결용
    sequence: int                # 실행 중 추가해도 재번호하지 않음
    device_key: str
    submission: SubmissionState
    completion: CompletionState
    attempt_id: str | None = None
    attempt_token: str | None = None
    receipt_number: str | None = None
    completion_evidence: str | None = None
~~~

이력의 UUID, 장비 접수번호, Windows JobId는 서로 다른 값이다. 같은 필드에 덮어쓰지 않는다. 접수번호만으로 매칭하지 않고 장비 식별·토큰·관측 범위를 함께 확인한다.

## 6. Canon 연결과 파서

### 6.1 현재 확인한 읽기 화면

호스트는 설치된 프린터 포트에서 읽고 로컬 설정으로 보정한다. 사용자 PC의 IP·계정·PIN을 소스나 배포 문서에 고정하지 않는다.

| 용도 | 실제 관찰한 경로 | 파싱 대상 |
|---|---|---|
| 로그인 진입 | /rps/ | 부서 ID/PIN 로그인 화면 식별 |
| 포털 | / 또는 /portal | 인쇄 가능 여부, 에러 정보 |
| 작업 상황 | /rps/jstatpri.cgi | 날짜/시각, 작업명, 사용자, 상황 |
| 작업 이력 | /rps/jlp.cgi | 접수번호, 종료시각, 출력 페이지수, 매수×부수, 종료코드 |
| 에러 | /rps/dstatus.cgi 의 CorePGTAG=9, PageFlag=d_sts2.tpl | 오류 상세 |
| 소모품 | /rps/dstatus.cgi 의 CorePGTAG=11 | 급지함, 크기, 잔량, 토너, 스테이플 |

관찰된 URL에는 Flag, LogType, CorePGTAG, Dummy 등의 매개변수가 있다. 실제 응답으로 필요한 조합을 검증한 후 어댑터 내부에서 구성한다. 이전 화면의 Dummy 값을 영구 설정에 저장하지 않는다.

### 6.2 클라이언트 구현

- Python 3.12 표준 라이브러리 urllib.request + http.cookiejar + html.parser를 우선 사용한다. 추가 패키지 없이 가능한지 1단계에서 검증한다.
- 응답이 브라우저의 JavaScript 실행에 의존한다면 실제 데이터 요청을 확인한 후 조회 계약을 확정한다. 파악하지 못한 요청을 추측해서 구현하지 않는다.
- 앱 사용 중에는 자체 HTTP 클라이언트로 조회한다. 이번 조사에 사용한 Codex 브라우저 세션을 배포 앱의 의존성으로 삼지 않는다.
- 로그인 성공은 HTTP 200이 아니라 포털/상태 화면의 필수 구조로 판정한다. 로그인 페이지가 다시 오면 AUTH_REQUIRED다.
- 저장된 자격 증명이 있을 때 세션 만료에 대한 재인증은 1회만 시도한다. 인증 거부 시 반복 제출하지 않는다.
- 지정 장비의 검증된 origin으로만 인증정보를 보낸다. 다른 호스트/미승인 포트로 리다이렉트될 때 인증 POST·쿠키를 전달하지 않는다.
- 인증 쿠키는 프로세스 메모리에만 유지한다. 브라우저 쿠키 추출을 구현하지 않는다.
- HTTPS는 정상 인증서 검증을 사용한다. 현재 관찰된 HTTP 연결은 로컬 장비 연결 방식으로 명시하고, 조용히 인증서 검증을 끄거나 프린터 네트워크 설정을 바꾸지 않는다.
- 소켓 제한 시간, 읽기 전체 deadline, 응답 크기 상한을 둔다. 초기값은 소켓 3초, 응답 2 MiB 상한, 요청 전체 5초 목표로 검증한다. urllib의 timeout 하나가 전체 deadline을 보장한다고 가정하지 않는다.
- HTML 인코딩은 응답 헤더·meta와 검증된 장비 인코딩을 따른다. 해석 실패는 “조회 형식 확인 필요”로 처리한다.

쿠키·타임아웃·HTML 처리의 기반은 [urllib.request](https://docs.python.org/3.12/library/urllib.request.html), [http.cookiejar](https://docs.python.org/3.12/library/http.cookiejar.html), [html.parser](https://docs.python.org/3.12/library/html.parser.html)에서 제공한다.

### 6.3 파싱 규칙

- 표의 위치 번호가 아니라 헤더 집합으로 표를 찾는다. 예: 급지위치 / 용지 잔량 / 용지 크기 / 명칭.
- 잔량 셀의 텍스트와 이미지 alt/title을 함께 읽는다. 실제 화면은 “양호” 텍스트와 “66-100%” 이미지 설명을 함께 제공했다.
- NBSP, 줄바꿈, 전각 기호, x/×를 정규화한다.
- “양호”만 있으면 level=OK, percent_range=None. 100%로 바꾸지 않는다.
- 정상적인 빈 작업 표와 인증/파싱 실패로 표를 못 읽은 경우를 구분한다.
- 장비의 지역 시각은 설정된 시간대와 함께 보존한다. PC 시각과 같다고 가정해 작업을 오매칭하거나 처리 시간을 계산하지 않는다.
- 오류 상태의 원문은 로컬 진단에 필요한 짧은 범위만 보존한다. HTML 전체·계정·쿠키·학생 파일명을 일반 로그에 덤프하지 않는다.
- 공개되지 않은 문구는 UNKNOWN 처리한다. 정상으로 추측하지 않는다.
- 무관한 다른 사용자의 완료 이력은 앱 JSONL에 복제하지 않는다.

### 6.4 자격 증명

연결 창에서 부서 ID와 PIN을 입력받고, “이 PC에 저장”을 선택했을 때만 Windows Credential Manager의 앱 전용 Generic Credential에 저장한다.

~~~python
class CredentialStore(Protocol):
    def load(self, device_key: str): ...
    def save(self, device_key: str, department_id: str, pin: str) -> None: ...
    def delete(self, device_key: str) -> None: ...
~~~

ctypes로 CredReadW / CredWriteW / CredFree 등을 감싸며 플랫폼 API 접근은 이 모듈에 한정한다. 조회는 앱이 만든 정확한 target name만 대상으로 한다. JSON 설정에는 연결 주소와 저장 항목 참조만 둔다. [Microsoft CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew)

## 7. 상태 감시와 오류 알림

### 7.1 조회 주기 초안

| 상황 / 정보 | 초기 주기 | 처리 |
|---|---|---|
| 출력 중 장비 오류·활성 작업 | 약 2초 | 실제 응답 시간에 따라 조정 |
| 처리 중인 앱 작업의 완료 이력 | 활성 목록에서 사라질 때 즉시, 추적 중 주기 조회 | 목록에 잠깐도 안 나타난 짧은 작업도 확인 |
| 스테이플·토너·A4 잔량 | 약 10초 | 시작·오류·재개 요청 때 추가 갱신 |
| 출력 없는 상태 | 약 15초 | 앱 시작을 네트워크로 지연시키지 않음 |
| Tk 상태 반영 | 200ms 간격 최신 상태 확인 | 변경된 표시만 갱신 |
| 연결 실패 | 2→5→10→30초 상한 | 추가 전송은 먼저 보류 |

정보마다 마지막 성공 시각을 따로 관리한다. 용지 조회 성공 때문에 실패한 작업 조회의 유효기간이 연장되지 않아야 한다. Tk와 제어기는 monotonic 시계를 사용해 모니터 자체가 멈춘 경우에도 오래된 정상 상태를 만료시킨다.

전송 직전 건강 상태·작업 추적 정보는 최근 5초 이내 유효값을 요구하는 것으로 시작한다. 정상 네트워크에서 이 조건을 만족하는지 측정한 후 주기/TTL을 함께 조정한다. 느린 조회를 정상으로 가장하기 위해 TTL만 무한히 늘리지 않는다.

### 7.2 병렬 실행과 알림

- 장비 조회 스레드 1개, 전송 스레드 1개, Tk 메인 스레드를 사용한다.
- 같은 장비 조회를 겹쳐 시작하지 않는다. CookieJar는 조회 스레드가 소유한다.
- 네트워크 대기·Sumatra 대기 중에 print_state_lock을 잡고 있지 않는다.
- 모니터는 장비 오류를 발견하면 제어기의 추가 전송 허가를 닫고, UI에 사건을 알린다.
- Tk의 after 폴링이 전달 큐를 읽어 위젯을 변경한다. 백그라운드에서 위젯을 직접 만지지 않는다.
- 일반 수치 갱신은 최신 1개로 합쳐도 되지만, 오류 발생·완료·재개 사건은 누락되지 않게 별도 보관한다.
- 첫 오류에 알림음과 비모달 알림창을 표시한다. 확인/음소거 전에는 상태 배지에 계속 남긴다. 갱신마다 팝업을 추가하지 않는다.
- 사용자 작업을 방해하는 반복적인 포커스 강탈 대신 작업표시줄 강조와 지속 배지를 사용한다.
- 알려진 오류는 즉시 알리고, 정보 조회 실패는 첫 실패에서 전송 보류 후 지속 실패 시 연결 경고를 표시한다.
- 장시간 변화 없음은 “정체 의심” 경고다. 페이지 수가 많은 정상 작업을 실패·미전송으로 바꾸지 않는다. 초기 경고 기준은 180초 또는 예상 상한의 2배 중 큰 값이며 실제 표본으로 조정한다.

장비 오류가 해소되어도 보류 원인은 사용자의 이어서 동작까지 유지한다. 서로 다른 원인이 겹치면 모두 해결돼야 재개할 수 있다.

## 8. A4 잔량과 예상 사용량

### 8.1 화면과 데이터 의미

기본 표시 예시:

~~~text
A4 카세트 1  66–100% · 양호
A4 카세트 2  66–100% · 양호
이번 작업 예상 사용량  342매
마지막 확인  3초 전
~~~

- 342매는 화면 설명용 예시다.
- 용지 크기는 공백·대소문자·A4R 표기를 정규화하되 원래 방향 정보도 남긴다.
- A3/B4와 크기를 모르는 수동급지대는 A4 공급량에 합치지 않는다.
- 카세트 1과 2의 퍼센트를 더하거나 평균 내어 “A4 총 잔량”으로 표시하지 않는다.
- 카세트 용량을 모르는 상태에서 퍼센트를 정확한 매수로 환산하지 않는다.
- 모든 A4 정보가 오래되면 “A4 잔량 확인 안 됨”으로 표시한다.
- 남은 용지와 필요한 매수를 정확히 비교하는 “이번 작업 충분” 판정은 1차 범위에서 제외한다. 센서 구간과 급지함 용량/사용 조건이 추가 검증돼야 한다.

### 8.2 예상 사용 매수 계산

원본 PDF의 쪽수를 그대로 종이 매수로 쓰지 않고 전송 레이아웃을 반영한다. 준비된 파일이 있으면 실제 전송 PDF의 쪽수를 사용한다. 아직 준비하지 않은 작업의 전체 예상량은 기존 페이지 수 캐시/사전검사 결과와 검증된 4분할 규칙인 ceil(원본 쪽수 / 4)로 계산하고, 전송 준비 후 실제 쪽수와 대조한다. 수량 표시만을 위해 전체 PDF를 미리 변환하거나 반복 변환하지 않는다.

~~~python
from math import ceil

def estimated_a4_sheets(prepared_pages: int, copies: int, duplex: bool) -> int:
    sheets_per_copy = ceil(prepared_pages / 2) if duplex else prepared_pages
    return sheets_per_copy * copies
~~~

- 각 전송 작업·각 부 단위로 올림한다. 여러 PDF의 홀수 마지막 쪽을 서로 같은 종이에 배치한다고 계산하지 않는다.
- 이름 구분지·OMR·일반 구분지는 build_print_jobs에 이미 포함되므로 한 번만 센다.
- 묶음 인쇄는 확장된 job.copies를 사용해 부수를 중복 곱하지 않는다.
- 이 값은 출력 준비물 기준의 예상 소비량이다. 용지 걸림으로 버린 종이, 장비 재출력, 외부 작업의 소비는 포함하지 않는다.
- 장비가 보고한 원고 쪽수·출력 쪽수·실제 매수를 서로 다른 단위로 유지한다.

### 8.3 A4 경고 규칙

| 관측 | 앱 반응 |
|---|---|
| 한 A4 카세트가 낮고 다른 사용 가능 A4 카세트가 충분 | 잔량 주의 표시, 계속 진행 |
| 사용 가능한 A4가 모두 낮음 | 보급 권고, 오류로 단정하지 않음 |
| 사용 가능한 A4가 모두 없음 | 추가 전송 보류, A4 보급 알림 |
| 용지는 있지만 지정 급지함/종류가 맞지 않음 | 장비 오류 내용과 함께 급지 조건 확인 |
| 사용 가능한 급지함 여부 자체가 미확인 | 부족 여부는 미확인, 장비 오류를 별도로 감시 |
| B4 카세트만 비어 있음 | A4 작업을 중단시키지 않음 |
| 조회 실패 | 잔량 미확인 표시, 0%로 처리하지 않음 |

“사용 가능”은 A4 크기뿐 아니라 급지함 사용 설정·용지 종류도 포함한다. 급지 조건이 검증되지 않았다면 잔량만으로 전송을 막는 판정을 활성화하지 않는다. 실제 장비의 용지 부족 오류는 별도로 전송을 보류한다.

## 9. 블록 순서와 정확한 작업 매칭

### 9.1 순서 통제 범위

- 실행 순서는 기존 build_print_jobs의 결과를 그대로 따른다.
- 이름 구분지 → OMR → 시험지 → 다음 작업의 경계까지 같은 장비의 완료 확인을 적용한다.
- 세로/가로/A:ble로 바뀌어도 다른 프린터인 것처럼 새 전송 허가를 얻지 못한다.
- 한 물리 장비에 기본 6건의 롤링 선전송 창을 사용한다. 정상 출력 중에는 인쇄 중 1건과 대기 약 5건을 목표로 하며, 창 밖 작업은 보내지 않고 장비가 여러 대여도 임의 병렬화하지 않는다.
- 같은 PC의 앱 중복 실행은 정규화한 장비 식별 기반 Windows named mutex로 전송만 상호 배제한다. 다른 인스턴스도 상태 조회는 가능하다.
- 장비 식별은 프린터 포트의 주소를 발견한 뒤 Remote UI의 제품/장비 식별값으로 검증한다. 비공개 식별값은 로컬에만 두고 device_key에는 안정적인 해시를 사용한다. 같은 주소에서 다른 장비가 확인되면 기존 작업 매칭과 ETA 표본을 이어 쓰지 않는다.
- 시작 시 이미 장비에 남아 있는 작업을 확인한다. 기존 작업이 보이면 종료될 때까지 보류한다.
- 다른 PC·복사·다른 부서 작업의 끼어들기를 앱이 완전히 막지는 못한다. 앱 내부 작업 사이의 순서를 통제하는 범위와 외부 작업 개입 가능성을 구분한다.

### 9.2 같은 파일을 여러 번 출력해도 구분하기

OMR·이름 구분지·동일 시험지가 반복되므로 파일명/시각의 대략적인 일치만으로 완료를 판정하지 않는다.

1. 각 전송 시도에 새 attempt_id와 충돌 검사를 거친 짧은 ASCII 토큰을 만든다.
2. 최종 변환 PDF를 앱 전용 짧은 로컬 spool 디렉터리의 QP_<token>.pdf로 준비한다.
3. 원본 파일은 변경하지 않는다. 전송 사본의 해시를 원본/변환 이력에 연결한다.
4. 프린터 작업명에서 토큰을 확인하고 접수번호를 TrackedJob에 저장한다.
5. 활성 목록을 놓쳤어도 완료 이력에서 같은 토큰을 찾는다.
6. 장비 ID + 토큰 + 접수번호 + 시각 범위를 함께 확인한다.
7. 토큰이 누락·잘림·중복되면 NEEDS_REVIEW로 멈춘다. 같은 내용의 다른 작업을 대신 연결하지 않는다.
8. 성공 완료 또는 사용자의 명시적 정리 후에만 전송 사본을 제거한다. 미확정 파일은 보존한다.

권장 위치는 사용자 로컬 앱 데이터 아래 QuickPrinter/spool이다. 경로 길이 제한을 확인하고, 프린터가 출력하는 전체 경로에서 토큰까지 보이는지 반드시 시험한다. PDF 메타데이터 제목이 대신 표시되거나 전송 하나가 여러 장비 작업으로 쪼개진다면 이 단계에서 매칭 계약을 다시 확정한다.

사본을 준비한 뒤 검증된 변환 PDF와 바이트 해시가 같은지 확인한다. 복사 도중 원본 서명이 바뀌면 전송 전에 중단한다. 임시 파일 정리는 앱이 만든 spool 하위 경로와 해당 attempt_id에 속한 파일만 대상으로 한다.

### 9.3 전송 상태별 재개 규칙

| 상황 | 기록/상태 | 다음 동작 |
|---|---|---|
| PDF 준비 실패 / 프로세스 생성 전 실패 | NOT_SENT | 원인 해결 후 재시도 가능 |
| 프로세스 시작 이후 대기 | IN_FLIGHT | 다음 전송 차단 |
| Sumatra 정상 반환 | CALL_CONFIRMED | 장비 완료 확인 대기 |
| Sumatra 시간 초과·오류 반환 | UNCONFIRMED | 장비 토큰 대조, 자동 재전송 금지 |
| 장비에 토큰 접수됨 | ACCEPTED / PROCESSING | 같은 접수번호를 계속 추적 |
| 장비 이력 OK 종료 | DEVICE_CONFIRMED | 필수 완료 이력 저장 후 선전송 창 한 자리 보충 허가 |
| 장비 실패/취소/부분 출력 | FAILED / CANCELLED / NEEDS_REVIEW | 출력물 확인 후 별도 재인쇄 판단 |
| 연결 끊김/로그인 만료/응답 해석 실패 | 실행 보류 | 기존 접수번호 유지, 재접속 후 대조 |
| 보급 후 기존 작업이 장비에서 자동 완료 | 완료 사실 기록 + 실행 보류 유지 | 사용자의 이어서 동작 후 다음 미전송 작업 |
| Windows 대기열만 0개 | 완료 미확인 | 성공 처리하지 않음 |

완료 조건은 “토큰이 일치하는 해당 작업의 성공 종료 기록”이다. 큐 비움, 프린터 ready, 카운터 증가만으로 대신하지 않는다. Windows의 PRINTED/COMPLETE도 항상 종이 출력 완료를 보장하지 않는다. [Microsoft JOB_INFO_2](https://learn.microsoft.com/en-us/windows/win32/printdocs/job-info-2)

### 9.4 실행기 의사코드

~~~python
def execute_next(runtime):
    job = runtime.first_definitely_unsent()
    prepared = runtime.prepare_pdf_and_unique_token(job)
    runtime.audit_required("job_attempt", job, prepared)

    # 오류 감지와 프로세스 시작 사이의 경쟁 조건도 이 함수에서 처리한다.
    # 최신 관측/보류 상태 확인 + 현재 작업 예약 + Popen 시작만 짧게 잠근다.
    process = runtime.start_guarded(prepared)

    if process is None:
        runtime.record_attempt_not_started(job)
        return  # 아직 전송하지 않았으므로 보류 후 재개 가능

    try:
        result = runtime.wait_for_dispatch_call(process)
    except Exception as error:
        runtime.mark_unconfirmed(job, error)
        runtime.reconcile_from_device(job)
        return  # 미확정 작업을 일반 retry_batch에 넣지 않는다

    if not result.success:
        runtime.mark_unconfirmed(job, result.error)
        runtime.reconcile_from_device(job)
        return

    runtime.mark_call_confirmed_in_memory(job)
    # 이 저장이 실패해도 전송 사실은 메모리에 남고 재전송되지 않는다.
    runtime.audit_required("job_submitted", job)

    outcome = runtime.wait_for_device_result(job)
    if outcome.successfully_completed:
        runtime.mark_device_completed_in_memory(job, outcome)
        runtime.audit_required("job_device_completed", job, outcome)
        runtime.release_completed_slot(job)
        # 오류 보류가 걸렸다면 슬롯이 비어도 다음 전송은 허가되지 않는다.
    else:
        runtime.hold_for_review(job, outcome)
~~~

- 전송 허가를 계산한 뒤 오류가 들어왔으면 아직 시작하지 않은 Popen을 취소한다. 이미 시작된 호출은 취소 성공을 가정하지 않는다.
- 모니터는 Sumatra가 멈춰 있는 동안에도 상태와 알림을 갱신한다.
- 예상하지 못한 예외는 “미전송”으로 분류하지 않는다. 프로세스 시작 여부를 기록해 판정한다.
- 출력 완료가 Sumatra 반환보다 먼저 관측되어도 보관한다. 전송 호출과 완료 사실을 각각 기록한다.
- 전송 호출이 아직 진행 중이면 장비 완료만 보고 다음 호출을 시작하지 않는다.
- 필수 이력 저장 실패는 이후 전송 허가를 닫는다.

### 9.5 중지, 재개, 큐 수정, 종료

- start_print_thread의 우선순위는 “미확정 대조 → 보류 실행 재개 → 기존 활성 실행에 추가 → 미전송 재시도 → 새 실행”이다.
- Ctrl+Shift+Enter도 같은 진입점을 사용한다.
- 오류 보류 중에는 아직 예약되지 않은 새 블록을 편집할 수 있다. 예약된 작업은 원래 순서와 설정을 유지한다.
- 전송 중지 후에도 이미 보낸 미완료 작업은 감시한다. 인쇄 스레드가 끝났다는 이유로 완료 원장과 보호 ID를 지우지 않는다.
- 재개는 이전 미완료 작업을 먼저 대조하고, 이후의 NOT_SENT 작업만 보낸다.
- undo·삭제·다중 드래그가 장비 미완료/미확정 상태를 되돌리거나 보호를 해제하지 못하게 한다. 출력 원장은 UI undo 스냅샷의 복원 대상이 아니다.
- queue_block_status는 해당 작업의 출력 원장 상태를 먼저 반영한다. undo가 예전 block_status_by_id 값을 복원해도 완료/미확정 작업이 새 대기로 바뀌지 않아야 한다.
- 완료된 블록 복사/붙여넣기는 지금처럼 새 UUID의 새 대기 작업이 된다.
- 앱 종료는 추가 전송을 멈추고 모니터를 정리한다. 이미 장비에 들어간 작업은 계속될 수 있다는 기존 안내를 유지한다.
- 앱 재시작 시 큐와 재시도 목록을 자동 복원하지 않는다. 장비의 남은 작업은 표시만 하고 자동 재출력하지 않는다.

## 10. 완료율과 예상 남은 시간

### 10.1 진행률

세 가지 수치를 분리한다.

- 전송 완료: Sumatra 호출 성공 수 / 전체 전송 작업 수.
- 출력 완료: 장비 성공 종료가 확인된 블록 수 / 전체 블록 수.
- 예상 출력 매수: 준비된 PDF에서 계산한 A4 매수. 장비가 실제 보고한 출력 매수와 별개다.

블록 완료는 해당 블록의 구분지·OMR·본문 등 모든 하위 작업이 성공 종료했을 때만 증가한다. 진행 중 페이지 수가 제공되지 않으면 블록/작업 단위로 갱신한다.

### 10.2 계산 방법

- 제조사 최고 속도만으로 시간을 확정하지 않는다.
- 새 순차 전송에서 수집한 정상 작업 표본을 사용한다.
- 표본에는 개별 작업 준비 시작부터 장비 성공 종료 관측까지의 monotonic 시간을 저장하고, 준비/호출/완료 대기 시간도 나눠 남긴다. 초기 전체 사전검사는 별도의 준비 단계로 표시한다.
- 오류·연결 끊김·사용자 대기·확인된 외부 작업 개입이 있던 표본은 학습에서 제외한다.
- 현재 이력의 “장비 시작시각~종료시각”에는 대기 시간이 포함될 수 있으므로 이를 바로 장당 출력 속도로 사용하지 않는다.
- 경로/양면/스테이플/4분할/작업 크기 구간별 최근 표본을 최대 20개씩, 전체 최대 512개 유지한다.
- 정상 표본이 3개 미만이면 “계산 중”. 다른 구간 표본을 빌릴 때는 “초기 예상”으로 표시한다.
- 1차 알고리즘은 구간별 장당 소요 시간의 중앙값과 하위/상위 분위값을 사용한다. 작은 작업 구간을 별도로 둬 작업 전환·스테이플 고정 비용의 영향을 줄인다.

~~~python
def estimate_pending_seconds(jobs, model):
    low = high = 0.0
    for job in jobs:
        band = model.seconds_per_sheet_band(job.profile_bucket)
        if band is None:
            return None
        low += job.estimated_sheets * band.low
        high += job.estimated_sheets * band.high
    return low, high
~~~

이 범위는 통계적으로 보장된 신뢰구간이 아니라 운영상 예상 범위다. 진행 중 작업은 시작 후 경과와 관측 상태로 보정하되, 정보가 부족하면 범위를 넓히거나 “완료 확인 중”으로 표시한다. 완료 기록이 없는데 0초/100%를 표시하지 않는다.

- 남은 시간에는 아직 보내지 않은 작업과 이미 보냈지만 끝나지 않은 작업을 모두 포함한다.
- 작업 추가 시 분모와 ETA를 다시 계산한다.
- 순서 우선 모드에서는 기존 전송량 12개/재충전 6개를 유지하는 방식보다 작업 사이 대기가 늘 수 있다. 완료 조회 지연과 실제 처리량을 측정하며, 속도를 높이기 위해 미완료 작업 제한을 임의로 풀지 않는다.
- 스테이플/용지/연결 문제로 보류되면 완료 예정 시각을 숨기고 “보급 대기 / 재개 후 재계산”으로 바꾼다.
- 네트워크 조회 지연도 관측 오차이므로 작은 초 단위 수치 대신 “약 8–11분” 같은 범위를 표시한다.
- 시간 계산에는 PC monotonic 값을 사용한다. 장비 시계와 PC 시계 차이는 진단값으로만 남긴다.

## 11. 화면과 기존 조작 유지

### 11.1 기본 화면

기존 탭 5개, 3:7 배치, 큐 행 높이, 글꼴, 단축키는 유지한다.

- 기존 상단 상태 배지: 인쇄 중 / 스테이플 보급 대기 / 연결 확인 필요 / 출력 완료.
- 기존 하단 현재 작업 줄: “출력 73/101블록 · 약 8–11분 · A4 양호” 정도로 요약.
- 상태 배지를 클릭하면 “프린터 상태” 상세 창을 연다.
- 상세 창에 카세트별 A4 범위·갱신 시각·스테이플·토너·현재 작업·전송/완료 수·연결 상태를 표시한다.
- 상세 창에서 연결 설정, 다시 조회, 알림음 끄기, 해결 후 이어서, 미확정 작업 확인을 제공한다.
- 순서 우선 모드에서는 기존 전송 묶음/재충전 기준 입력을 비활성화하고 완료 확인 방식이라는 설명을 붙인다. 값은 호환 설정으로 보존한다.
- 큐 배지는 대기 / 예약 / 전송 중 / 출력 대기 / 출력 중 / 완료 / 보류 / 확인 필요로 명확히 구분한다. “출력 중”은 장비가 그 상태를 보고한 경우에만 사용한다.

    eta_text: str

~~~

뷰 모델 생성은 순수 함수로 테스트한다. Tk 타이머는 최신 모델과 이전 모델을 비교해 변경된 라벨만 갱신한다. 잔량 조회마다 전체 큐를 다시 그리거나 PDF를 다시 읽지 않는다.

표시 우선순위는 확인 필요/오류 보류 → 연결 보류 → 출력 진행 → 일반 대기다. 기존 append 함수의 set_status("인쇄 전송 중") 같은 호출이 오류 배지를 덮어쓰지 않도록, 새 모드의 표시는 제어기 상태에서 한곳으로 모아 계산한다.

해상도 1280×720 및 현재 운영 화면의 배율에서 줄바꿈·잘림·버튼 접근성을 확인한다. 네이티브 제어가 제공되지 않는 환경에서는 우회 도구로 테스트했다고 주장하지 않고, 지원되는 환경 또는 운영자의 확인으로 보완한다.

### 12.2 이력 이벤트

기존 이벤트 의미를 유지하고 아래를 추가한다.

| job_device_completed | 접수번호, 장비 종료시각, 출력 단위, 결과 코드 |
| job_reconciliation_required / job_reconciled | 불명확 사유, 연결 근거, 사용자 확인 종류 |
| run_output_completed | 장비 확인 완료 수, completion_evidence |

- job_attempt는 실제 전송 전에 필수 저장한다.
- job_submitted와 job_device_completed의 저장 실패는 이후 전송을 중단한다. 이미 보냈거나 끝난 사실은 원장에 남긴다.
- 기존 physical_output_verified는 장비 이력만으로 True로 바꾸지 않는다. completion_evidence="canon_job_log", device_completion_confirmed=True를 별도 추가한다.
- run_finished는 기존 전송 확인만 모드의 결과와 새 device_reported_completed 결과를 구분한다.
- 잔량은 변화 시에만 기록하고 조회마다 fsync하지 않는다. 장비 완료 등 재개 판단에 필요한 이벤트는 필수 저장한다.
- metrics 캐시는 개인·학생·문서명 없이 수량/옵션/시간 통계만 담고, 버전·장비 구성이 달라지면 무효화한다.
- 전송 사본, 인증정보, 원본 HTML, 장비 식별 상세, 이력, 성능 캐시는 Git와 배포본에서 제외한다.

## 14. 구현 순서와 단계별 완료 조건

### 단계 1 — 읽기 전용 연결 증명과 데이터 계약

구현: Canon 클라이언트, 파서, CredentialStore 인터페이스, 실제 응답 형식 기록.

산출물:
- 브라우저 없이 Python 클라이언트가 로그인 후 건강 상태·소모품·작업/완료 이력을 읽는 증거.
- 원본 응답은 로컬만 보관하고 테스트에는 비식별 fixture만 사용.
- 오류 시나리오 fixture는 실제 관측인지 합성인지 구분.
- 아직 모르는 인증 요청, 페이지 수 단위, 작업명 잘림과 세션 충돌을 명시.

통과 조건: 정상 조회와 인증/연결/형식 실패가 구분되고, 상태 조회 요청만 실행된다.

직접 조회가 성립하지 않으면 상태/ETA의 가짜 구현으로 넘어가지 않는다. 검증된 인증 경로 또는 장비의 읽기 전용 관리 인터페이스를 확정한 뒤 계속한다.

### 단계 2 — 감시·A4·스테이플 상태 표시

구현: DeviceSnapshot, 모니터, A4 집계, UI 뷰 모델·상세 창.

통과 조건:
- 화면 동결 없이 카세트별 A4 구간과 마지막 확인 시각 표시.
- 정상/부족/미확인과 인증 끊김을 분리.
- 앱 시작은 상태 조회 완료를 기다리지 않음.
- 현 단계의 화면 확인만으로 실제 전송 보호가 완성됐다고 배포하지 않음.

### 단계 3 — 고유 작업 매칭·장비 단위 순서 통제

구현: 전송 사본, 원장, guard, named mutex, 순차 실행, 장비 완료 대조.

통과 조건:
- 시뮬레이터에서 항상 장비당 앱 미완료 전송 ≤ 1.
- 단일 블록 내부 프로필 전환에서도 순서 보존.
- 전송 시간 초과의 불명확 작업이 자동 재전송되지 않음.
- 네트워크 조회와 전송의 독립 동작, 이력 실패 경계 검증.

고유 파일명과 장비 접수번호의 실제 연결은 아래 실물 검증 단계에서 확인한다. 그 전에는 “출력 순서 보장 검증 완료”로 표시하지 않는다.

### 단계 4 — 재개·기존 큐 기능 통합

구현: 메인 인쇄 버튼 우선순위, RetryBatch 분리, 보호 ID 수명, append/undo/삭제/복붙 연동.

통과 조건:
- 오류 복구 후 기존 장비 작업은 재전송하지 않고 다음 미전송만 진행.
- 진행 중 상태가 단순히 is_printing 한 변수로 소실되지 않음.
- 기존 단축키와 다중 드래그 회귀 통과.

### 단계 5 — 출력 완료율·예상 시간

구현: 준비 PDF 기준 매수 계산, 정상 표본 수집, ETA 범위, 캐시 무효화.

통과 조건:
- 실제 전송 수와 장비 완료 수가 분리됨.
- 보급/연결 대기 중 ETA가 감소하거나 완료가 되지 않음.
- 표본 부족 시 계산 중/초기 예상 표시.
- 오차 목표는 실측 후 정하며, 측정 전 정확도를 약속하지 않음.

## 15. 완료 판단 기준

- 스테이플/용지/장비 오류와 연결 확인 실패가 사용자에게 표시된다.
- 오류 후 새 작업을 계속 선전송하지 않는다.
- 프린터에 이미 들어간 작업을 자동으로 다시 보내지 않는다.
- 앱 작업 순서가 이름 구분지·OMR·시험지까지 유지되는 것을 검증한다.
- A4 잔량이 카세트별 센서 구간과 일치하며 미확인을 0%로 만들지 않는다.
- 장비 성공 종료 전에는 블록 완료와 전체 100%를 표시하지 않는다.
- 예상 시간은 아직 출력되지 않은 전체 분량을 포함하고 오류 중 보류된다.
- 기존 자료·부수·양면·스테이플·단축키·복붙·다중 드래그·실행 중 추가·이력 규칙의 회귀가 없다.
- 재시작은 빈 큐로 시작하고 과거 작업을 자동 출력하지 않는다.
- 자동 테스트 결과와 아직 실시하지 못한 실물 검증 항목을 구분해 기록한다.

우선 구현 단위는 “읽기 전용 연결 증명 → A4/스테이플 감시 → 작업 매칭과 순서 통제 → 재개 → ETA”다. 화면 표시만 먼저 만들어 문제 해결이 완료된 것으로 배포하지 않는다.
