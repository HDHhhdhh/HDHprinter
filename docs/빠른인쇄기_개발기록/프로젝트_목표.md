# 프로젝트 목표와 사용자의 염원

작성일: 2026-10-10. 현재 동작은 [제품 동작 정본](../../빠른인쇄기_제품동작_정본.md)을 기준으로 합니다. 날짜별 원본 기록의 범위는 [근거와 검증](근거와_검증.md)에 적었습니다.

## 시작점: 반복 인쇄를 한 번의 지시로 끝내기

2026-05-24의 첫 프로그램 요청은 단순했습니다. 과목, 회차, 시작 파일, 끝 파일, 부수를 고르면 파일을 순서대로 인쇄하는 도구가 필요했습니다. Canon iR-ADV 8585 III의 양면과 스테이플 설정도 함께 적용해야 했습니다.

파일마다 열기, 프린터 선택, 방향 변경, 부수 입력, 스테이플 설정을 반복하면 준비 시간이 늘고 실수도 생깁니다. 사용자는 그 반복을 줄이되 출력물의 순서와 마감 방식은 그대로 지키고 싶었습니다.

2026-07-26에는 목표를 다음처럼 표현했습니다.

> 말하자면 "인쇄 빠른 도구 상자" 같은 걸 만드는 거지.

이후 요청도 같은 방향입니다. 자주 쓰는 자료의 위치와 인쇄 프로필을 기억하고, 여러 학생의 주문을 큐로 가져오고, 인쇄 중에도 다음 작업을 편집하고, 멈추면 원인과 남은 작업을 알 수 있어야 합니다.

## 사용자가 실제로 줄이려던 비용

| 업무에서 발생하는 비용 | 사용자가 원한 결과 | 현재 구현의 연결점 |
|---|---|---|
| 파일을 찾고 같은 설정을 반복함 | 자료 종류를 고르면 맞는 파일·방향·인쇄 형식을 사용 | 카탈로그, 프린터 프로필, PDF 사전 검사 |
| 학생별 주문을 다시 입력함 | 서버 CSV를 한 번 가져와 여러 블록을 생성 | 안정된 자료 ID, CSV 검증, 이름 구분지와 OMR |
| 많은 블록을 마우스로 수정함 | 일반적인 키보드·선택·드래그 조작으로 처리 | 키보드 범위 구분, 다중 이동, 복사·붙여넣기, 이름 채우기 |
| 다음 작업을 준비하는 동안 프린터가 쉼 | 작은 문서도 충분한 대기를 유지하며 순서대로 보냄 | 장비 접수 확인, 기본 6건의 전송 창, 준비 작업 미리 수행 |
| 전송이 멈췄는데 알아차리지 못함 | 계속 표시되는 오류 알림과 작업표시줄 표시 | 상태 영역, 팝업, 알림의 중복 억제 |
| 앱이 끝났다고 해도 종이는 출력 중임 | 실제 장비 완료를 기준으로 진행률과 완료를 확인 | Canon 작업 토큰과 완료 기록 |
| 앱이 중단돼 큐를 다시 만들어야 함 | 보낸 작업을 중복 인쇄하지 않고 안전한 작업만 복구 | 영구 이력, 세션별 큐 백업, 명시적 복구 |
| 다른 PC에서 화면과 동작이 달라짐 | 코드·자료·글꼴을 같은 기준으로 설치 | Git 소스, Drive 자료, 해시 검증, 글꼴 설치 안내 |

## 사람이 정한 순서가 인쇄 순서가 되어야 함

큐는 인쇄할 파일의 목록만 보여 주는 곳이 아닙니다. 사용자가 학생과 자료의 출력 순서를 정하는 작업 공간입니다. 다음 작업은 순서를 보존해야 합니다.

- 여러 블록을 끌면 선택한 블록들이 기존 상대 순서를 유지하며 함께 이동합니다.
- 선택한 블록을 복사한 뒤 붙여넣으면 마지막 선택 블록 바로 아래에 새 블록이 들어갑니다. 선택이 없거나 인쇄·재시도 중이면 끝에 들어갑니다.
- 대량 주문서에서 가져온 새 묶음은 이름 가나다순으로 안정적으로 정렬합니다. 같은 학생의 자료는 CSV 안의 순서를 유지합니다. 기존 큐는 다시 정렬하지 않습니다.
- `가나다 정렬`은 사용자가 이미 만든 큐에 별도로 실행하는 명령입니다.
- 인쇄 중에도 아직 시작하지 않은 `예약`·`추가됨` 블록을 삭제할 수 있습니다. 이미 시작하거나 제출한 작업은 보호합니다.

화면 순서만 바꾸고 실행 작업 목록을 갱신하지 않으면 사용자의 뜻과 실제 인쇄가 달라집니다. 그래서 큐 편집과 전송 직전 검사는 같은 블록의 상태와 식별 정보를 확인해야 합니다. 관련 장애는 [오류와 해결](오류와_해결.md)에 기록했습니다.

## 같은 말처럼 보이지만 다른 세 가지 동작

### 큐 블록의 묶음 인쇄

초기 요청부터 의미가 정해져 있었습니다. 파일 `1, 2, 3, 4, 5`의 블록을 각각 5부로 설정하고 묶으면 출력 요청 순서는 다음과 같습니다.

```text
[1, 2, 3, 4, 5] × 5
총 25개 작업. 파일별 인쇄 설정과 스테이플을 유지.
```

파일 다섯 개를 병합해서 하나의 큰 PDF와 하나의 스테이플 세트로 만드는 기능이 아닙니다. 현재 우클릭 `묶기`는 원본 PDF 참조와 큐 순서를 보존합니다. 부수, 이름, 실제 프린터 대상, 배치와 방향이 맞는 블록만 묶을 수 있습니다.

### A:ble/APEX의 차시별 자료 조립

2026-09-19의 A:ble 요청은 선택한 여러 차시의 교재를 함께 찝고, 백지리뷰도 종류별로 함께 찝는 기능이었습니다. 이 경우는 자료 내부의 페이지 조립과 PDF 병합이 필요한 별도 동작입니다. 큐 묶음과 같은 규칙으로 바꾸면 안 됩니다.

### 전송 완료와 실제 인쇄 완료

Sumatra 호출이 성공하면 해당 작업을 보냈다는 뜻입니다. Windows 큐가 비면 Windows에서 더 처리할 작업이 보이지 않는다는 뜻입니다. 종이가 모두 나왔다는 사실까지 증명하지는 않습니다.

Canon 연동을 사용하면 앱은 작업 토큰의 장비 접수와 장비 완료를 따로 확인합니다. 완료 팝업도 이 완료를 기준으로 해야 합니다. Canon 연동이 없으면 Windows 큐 기준이라는 한계를 표시해야 합니다.

```mermaid
flowchart LR
    A[사용자 큐] --> B[PDF와 설정 확인]
    B --> C[전송 성공]
    C --> D[장비 접수 확인]
    D --> E[장비 완료 확인]
    E --> F[완료 알림]
```

각 화살표에는 별도의 확인이 필요합니다. 앞 단계의 성공을 뒤 단계의 완료로 바꾸어 표시하면 안 됩니다.

## 안전하게 멈추고, 남은 작업을 이어서 처리하기

사용자는 단순히 모든 오류를 무시하는 동작을 원하지 않았습니다. 정상적인 용지 사용이나 보충 때문에 불필요하게 멈추는 일을 줄이고 싶었습니다. 동시에 용지 걸림이나 스테이플 부족을 놓치면 안 됩니다.

현재 기준은 실제로 확인한 장비 응답과 급지 가능 여부입니다. A4 카세트 하나가 비어도 다른 카세트의 용지가 확인되면 용지 부족만으로 전송을 막지 않습니다. 특정 카세트 열림 코드도 실제 비교 검증을 거친 경우에만 다룹니다. 다른 카세트가 닫혀 있고, A4이며, 양수의 잔량 구간이 확인되어야 전송을 계속할 수 있습니다. 알 수 없는 상태를 용지 충분으로 간주하지 않습니다.

재개는 다음 원칙을 지킵니다.

- 이미 보낸 작업과 전송 여부가 불확실한 작업은 자동으로 다시 보내지 않습니다.
- 실행 중인 앱에서는 보관한 미전송 작업을 먼저 이어서 처리합니다.
- 새로 실행한 앱은 빈 큐로 시작합니다. 과거 큐 복구는 별도 명령으로 수행합니다.
- 복구는 전송 증거가 없는 완전한 블록만 허용합니다. 일부만 보낸 블록을 자동으로 잘라서 재인쇄하지 않습니다.
- PDF나 이력·복구 증거가 없으면 복구를 막고 검토 대상으로 남깁니다.

이 기준은 종이 낭비와 학생별 출력물 섞임을 줄이기 위한 것입니다. 기록을 남기는 기능과 다시 인쇄하는 권한은 분리합니다.

## 빠르다는 것은 사용자가 기다리지 않는다는 뜻

요청은 앱 시작, 블록 선택, 입력, 미리보기, 다중 이동, 파일 열기, 인쇄 요청을 모두 포함했습니다. 계산이 빨라도 화면이 멈추면 사용자는 느리다고 느낍니다. 그래서 다음 기준을 사용합니다.

1. 선택만 바뀌면 이력 저장, 합계 계산, 파일 검사를 다시 하지 않습니다.
2. PDF 분석과 파일·장비 작업은 UI 이벤트 처리를 오래 막지 않습니다.
3. 화면에 보이는 큐 행만 그리되 전체 스크롤 범위와 키보드 이동은 유지합니다.
4. 미리 준비하는 작업과 장비에 먼저 보내는 작업의 수를 각각 제한합니다.
5. 속도를 높여도 전송 증거와 접수 확인을 생략하지 않습니다.

현재 전송 창 기본값은 6건입니다. 대략 한 건 인쇄와 다섯 건 대기를 목표로 합니다. 실제 표시 개수는 작업 완료와 상태 갱신 시점에 따라 바뀝니다. 항상 정확히 다섯 문서가 대기한다는 보장은 아닙니다.

## 화면은 많은 정보를 빠르게 읽는 업무 도구

사용자는 새로운 시안도 검토했지만, 결국 기존 배치와 밀도를 우선했습니다. Aurora 테마는 취소했습니다. 현재 유지할 기준은 다음과 같습니다.

- 흰 헤더와 패널, 회색 본문, 파란 주요 버튼을 사용합니다.
- 오류·경고는 빨강, 예약 대기는 주황, 진행은 초록, 정상 준비·완료는 파랑입니다.
- 큐 이름은 파란 볼드, 서브탭과 과목은 검은 볼드, 나머지 세부 내용은 기본 글꼴로 표시합니다. `[일반]` 표시는 생략합니다.
- 블록 높이는 62px 수준을 유지합니다. 긴 제목이 한 줄에서 잘려도 블록 수를 더 많이 볼 수 있어야 합니다.
- 키보드 포커스와 비활성 상태를 구분합니다. 입력창의 Ctrl+A·복사·붙여넣기·실행 취소는 큐 명령과 충돌하지 않아야 합니다.
- 한국어 안내 문장은 가능한 한 어절 단위로 줄바꿈합니다. 입력값과 이력 원문은 그대로 유지합니다.
- 선택 블록을 떠날 때 유효한 수정은 자동 저장합니다. 검증 실패 시 입력과 선택을 유지합니다.

PDF 제작 기능은 취소되었고 `원본 경로 열기`로 바뀌었습니다. 현재 명령은 등록된 원본 PDF가 선택된 탐색기 창을 열어야 합니다. 임시 범위 PDF만 보여 주거나 새 인쇄를 시작하면 안 됩니다.

## 자료는 문제 번호보다 수업의 단원 범위로 고르기

교과서는 출판사·과목·문서·단원 범위로 고릅니다. `핵심문제`와 `핵심문제 변형`도 기존 문제 문서의 단원명에 맞춰 선택합니다.

선택한 중단원의 핵심문제와 그 중단원을 포함하는 대단원 평가를 함께 포함합니다. 변형의 `N-A/B/C`도 해당 원본 번호의 단원에 맞춥니다. 표지 1~2페이지는 한 번만 넣고, 본문 페이지는 중복을 제거한 뒤 원본 순서대로 인쇄합니다. 원본 핵심문제의 두 번째 표지는 해설 Drive 링크의 QR을 포함합니다.

현재 카탈로그는 검증한 42개 판본과 별도 변형 15종을 다룹니다. 확인이 불완전한 판본을 일부만 등록하거나 범위를 추측하지 않습니다. 판본 전체를 `pending`으로 두고 선택에서 제외합니다. 파일 수와 검증 기준은 [근거와 검증](근거와_검증.md)을 확인합니다.

## 다른 PC에도 같은 도구를 전달하기

배포 목표는 설치한 사람의 Codex나 Claude Code가 화면과 동작을 추측해서 다시 만드는 것이 아닙니다. 검증한 소스, 자료, 글꼴, 설치 안내를 받아 같은 기준으로 실행하는 것입니다.

공개 Git에는 코드·테스트·카탈로그·허용된 글꼴과 라이선스를 둡니다. 인쇄물 PDF 전체는 [저장소 README의 Drive 폴더](../../README.md)로 전달합니다. 실행 이력, 학생 정보, 인증값, 복구 스냅샷, 해당 PC의 시간 보정값은 전달하지 않습니다. Git 최신 코드에 연결할 때는 이전 Drive 배포본에서 `data`만 가져옵니다.

각 PC의 프린터와 자료 경로는 로컬 설정입니다. 다른 PC에서 소스를 수정해도 원격 저장소에 push하지 않으면 공유 소스가 바뀌지 않습니다. 배포의 재현성과 각 PC의 독립 운영을 함께 유지해야 합니다.

## 이후 개선을 판단하는 질문

새 구현은 다음 질문에 답할 수 있어야 합니다.

- 사용자가 반복하는 입력·확인·기다림 중 무엇을 줄이는가?
- 출력 순서, 스테이플 단위, 재인쇄 보호 기준을 유지하는가?
- 실제 동작을 확인할 방법이 있는가? 모의 검사와 실물 확인을 구분했는가?
- 코드 경계가 더 분명해지는가? 사용하지 않는 우회 경로가 늘어나지는 않는가?
- 다른 PC에서도 같은 자료와 설정을 연결할 수 있는가?

이 문서에서 제안하는 후속 기준은 새 기능 구현 승인이나 완료 선언이 아닙니다. 변경할 때 사용자의 원래 목적을 잃지 않기 위한 기준입니다.
